## 飞窗延迟与内存（下午）

- 飞窗冷启动延迟根因：每个自绘浮层必须是 WebContentsView（独立 renderer，空页面实测 69–72 MB，同站不合并）；`auto` 档 hover 预热来不及、`ready` 只等 did-finish-load、隐藏时 removeChildView 拆合成面。方案：A 预热前移（首帧后 idle）+ B overlay-ready 就绪判定 + C 打开路径减法 + D 隐藏期节流/冻结。
- 讨论了 Electron vs Chromium 层模型（views 树统一 vs DOM/原生两层）与 agent 软件（VS Code 把 webview 全部 iframe 化）内存更低的原因：它们无原生内容层、无多标签架构税、无 Ruffle。
- **决策：`webContents.clone()` 方案已否定**——复用源渲染进程与 Flash（PPAPI）单实例、Ruffle 按会话注入正面冲突。已补记到 docs/discussions/2026-11-25-electron-patch-backport-audit.md（第 2 节修正 + 第 4 节建议顺序划掉 #49959）。后续会话不要再把它作为内存优化路径翻出来。
- 内存优化剩余路径：`--process-per-site` / `--renderer-process-limit=N` 开关对照实验（audit 建议顺序第 1 条，0 风险 1 天）+ 飞窗预热 A/B/D。
- **动画掩盖方案已否决（demo：docs/design/overlay-masking-demo.html）**：自适应 transition 方案技术上成立，但用户实测判定冷开/热开差异仍可感知（"莫名的抖动卡顿"），不采纳。预热前移方案也被用户否决（用户可能不点，5 分钟空占内存——这正是当初选 hover 预热的原因）。飞窗延迟问题的处置待定，两条路都堵上后需重新讨论优先级。
- **新方向（外部回复评估通过）：浮层寄居外壳渲染进程**。核心洞察：clone 的否决理由（PPAPI 单实例、Ruffle 会话注入）只约束页面进程，外壳进程无 Flash/Ruffle，浮层寄居不在否决范围。API 链路已在 Electron 39 d.ts 核实：`setWindowOpenHandler` 的 `createWindow(options) => WebContents`（"instead of new BrowserWindow"，官方注释明说可用于以 BrowserView 形态打开，:19414）+ `WebContentsViewConstructorOptions.webContents` adopt 语义（:23195）+ `incrementCapturerCount`（:21881，隐藏保活的零 patch 替代，优先于内核 patch）。待验证：file:// site 判定下进程复用是否真发生（PID）、外壳主线程争用、shell-overlays.ts sender() 安全校验适配（最大工程量）。验证顺序：先 demo（window.open + createWindow 返回 WCV.webContents + 挂 contentView），通后再立项全链路改造。

## 飞窗共享进程：常驻预热落地 + overlay.prewarm 三档（晚）

- **交互前提出的"抢焦点/吞键"前提被证伪**：探针 `app/scripts/probe-overlay-focus.cjs` / `probe-overlay-focus-background.cjs` / `probe-overlay-focus-controlled.cjs` 在"前台悬停开窗 / 应用在后台 / 用户正在记事本打字"三种场景下，2 ms 采样 `win.isFocused()` / `getFocusedWebContents()` / `document.hasFocus()` 全程不变，guest 从未成为焦点。
- **真正的拦路虎是地址栏草稿被状态广播清空**：`BAO_OVERLAY_PREWARM=always` 跑前台套件整片 30 s 超时（= 交接文档的"7 条随机失败"）。应用内埋点抓到 `open-start 415 → open-done 426 → submit 444 value=""`：外壳启动后首份状态广播落在用户输入之后，`watch([active.id, active.address])` 把输入框重置成 `active.address`（NTP 是空串）→ 回车导航到空地址。常驻预热把这次广播推到"用户已填好地址"之后，于是从偶发变必现。
- **两处修法**：① `addressDirty`（用户敲过且未提交时，状态广播不覆盖；提交/失焦后跟随标签）——第一版用"值与上次同步不同"判断，把程序化切标签也当输入，把 `Ctrl+,` → 设置页用例钉死在旧地址（已被用例抓到）；② 常驻预热挪到 `window.show()` 之前，窗口不可见时建文档，与用户输入永不可能重叠（代价：启动期多付一次开窗 ~40 ms）。
- **契约：主进程决定、外壳执行**。`overlay.prewarm` 三档此前完全一致：`never` 悬停照样 `window.open`、建完不回收；`always` 在共享模式下主进程 `prewarm()` 是空操作（根本没人建）。现在 `can-prewarm`（只回答）+ `prewarm`（外壳请求）/ `overlay-prewarm`（主进程推，用于启动/切档/自愈后），判定点唯一在 `shell-overlays.ts::canPrewarmNow()`。`BAO_OVERLAY_PREWARM` 可强制档位供测试；`shared-mode` 分支里还有一行永不执行的死 return（闸门从未生效）。
- **验收（最终版本，全部实跑）**：隐藏并行 28 文件 0 失败 79 s；前台串行默认档 **70/70** 167 s；`BAO_OVERLAY_PREWARM=always` **70/70** 171 s；`BAO_OVERLAY_SHARED=0` **70/70** 172 s。常驻档的套件代价仅 ≈4 s（+6 MB 内存），此前被挡回是地址栏竞态而非价格。
- 新增 `tests/smoke/overlay-prewarm-policy.test.cjs`（3 条，前台专用，显式钉死各档 env，避免被外层 `BAO_OVERLAY_PREWARM` 覆盖）。文档：`docs/discussions/2026-11-25-overlay-shared-process-demo.md` §7。
- 未做：待决 3（`PerformanceObserver('longtask')` 开发期告警）、待决 4（合并 heap 后的 GC/帧预算完全没测）。常驻仍非默认（`DEFAULT_SETTINGS.overlayPrewarm = auto`），改默认留给产品决定。

## 测试提速工具：`--only` / `--changed`（2026-11-25 深夜）

- 起因：每次都跑全量冒烟（隐藏 ~80 s、前台 ~165 s）太贵。**先排除了"加并发"这条路**：32 逻辑核上 4 并发 79–88 s、8 并发 84 s，单文件耗时反而翻倍（tearoff 45→84 s）——瓶颈是每个用例都要冷启动一个 Electron 应用 + 固定等待，不是 CPU。
- 新增 `app/scripts/test-map.cjs`：手写的「改动路径 → 冒烟用例」近似依赖表（不是自动推导——Electron + IPC + 渲染层三张网里扫 require 不可靠，手写表可审阅）。命中规则取并集；`browser-window.ts`/`package.json`/`preload/index.ts` 等全局文件返回 `null`=全量；`src/` 下没有规则的新模块也退回全量（宁可多跑）；文档/记忆改动不跑用例；改某个用例文件只跑它自己。
- `scripts/test.cjs` 新增 `--only=name[,name]`、`--changed[=<ref>]`：都解析成文件子集后走原有调度（长文件优先、durations 缓存）。耗时估算按并发折算（`max(总量/jobs, 最长文件)`），一开始忘了折算把全量估成 10 min（实际 2 min）。
- `package.json` 新增 `smoke:file`（= `test.cjs smoke`，配 `-- --only=`）与 `smoke:changed`。
- 验证：`--only=quick-settings,theme` 实跑 12.3 s；`--changed` 在当前工作区（含 package.json）正确退回全量并打印 "40 个改动 → 全量（package.json 影响全局），约 2 min"；映射函数 9 组路径单测通过；全量隐藏仍是 28 文件/0 失败/88.5 s。
- 用法分层：日常 `smoke:file --only=<受影响的>`（8–25 s）→ 提交前 `npm run smoke`（~80 s）→ 换内核/动窗口·焦点·输入 `--foreground --serial`（~165 s）。
