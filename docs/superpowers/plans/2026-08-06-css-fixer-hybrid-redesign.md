# 方案C修复版：混合式 CSS 修复（主进程安全转译 + 页面运行时）

> 状态：设计草案（未改代码）
> 日期：2026-08-06
> 目标：在保留脚本平台运行时能力的前提下，把"纯文本转译"移到主进程以消除 FOUC 并减轻平台负担。这是对已回退的 C 方案的**架构修正版**。

## 为什么原版 C 失败（必须认识的前车之鉴）

原版把 `rewriteCssText` 全量搬到主进程 URL 层，导致：
1. **全表替换破坏性**：拦截 `bf-css-patch://` 后，任一 fetch/解析失败返回 502/空 → 整张样式表消失 → 站点崩（7k7k 全线崩溃实证）。
2. **`:has`/container 运行时被拆到 preload**：时序/上下文与页面主世界不匹配 → 三徽章/柱状图标记设不上。
3. **拦截盲区**：内联 `<style>`、JS 动态插入、非 `.css` 后缀、`@import` 递归全拦不到。
4. **CSP/mixed-content**：https 页拦截自定义 scheme 需 `bypassCSP`，且旧站 http 环境更脆。

**根子：CSS Fixer =「文本转译」+「页面世界运行时」两件事。** 原版把前者全拿走、后者硬拆，破坏自洽，还在 URL 层引入全表替换的破坏性。

---

## 修复版的核心理念

**只把"纯文本、无 DOM 依赖、绝对可逆"的转译放主进程；凡涉及 DOM 的运行时一律留在页面世界。且主进程转译失败时必须原样放行，绝不让任何样式表消失。**

划分依据：

| 能力 | 依赖 DOM？ | 归属 |
|------|-----------|------|
| `:where` / `:is` 解包 | 否 | 主进程（纯文本） |
| `@layer` 展平 | 否 | 主进程 |
| `dvh`→`vh` | 否 | 主进程 |
| 颜色转换 | 否 | 主进程 |
| `:has` 标记运行时 | **是** | 页面世界（不动） |
| container-query 运行时 | **是** | 页面世界（不动） |
| 动态 `<style>` / JS 插入 | **是** | 页面世界（不动） |

---

## 架构设计

### 主进程：`css-patch-service`（重写版）

只对**通过 `<link>` 加载、URL 以 `.css` 结尾的请求**做拦截（严格白名单，杜绝盲区误伤）。

```
webRequest.onBeforeRequest
  └─ url 匹配: /\.css($|\?)/ 且 非 loopback 且 非 data:/blob:
      └─ 重定向到 bf-css-patch://sheet?src=<orig>
           └─ handler:
               fetchText(src)  →  失败 → 返回原始 CSS（绝不 502）
               isCss(text) 校验（含 { 且非 HTML 标签开头且无 <）→ 否则原样返回
               rewriteCssText(text)  →  抛错 → 原样返回
               (never blocks, never empties)
```

### 页面世界：极简 preload 运行时（不是完整 Fixer）

只保留两段 vendored JS + MutationObserver 标记：
- `vendor/css-has-pseudo.js`（`:has` 标记 + 动态重算）
- `vendor/container-query-polyfill.js`
- 自己的 `markHasInSheets` / `scheduleMarkHas` / MutationObserver

即：**删掉 entry.ts 里的 fetch + rewrite + link 替换逻辑**，因为这些已由主进程完成；运行时只做 DOM 标记。

### 关键差异点（对比原版）

| 项 | 原版（失败） | 修复版 |
|----|------------|--------|
| 拦截范围 | 所有 `.css` | 严格 `.css` 白名单 + 内容校验 |
| fetch 失败 | 502 → 丢表 | **返回原始 CSS** |
| rewrite 抛错 | 崩 | **原样返回** |
| `:has` 运行时 | 拆 preload，时序乱 | 保留完整页面世界运行时 |
| CSP | 需 bypassCSP | 仍需（https），但容错保证不崩站 |
| 动态样式 | 拦不到 | 运行时 MutationObserver 兜底 |

## 收益（相对脚本平台）

| 维度 | 脚本平台 | 方案C修复版 |
|------|---------|------------|
| 首帧无 FOUC | ❌ | ✅（主进程源头改写） |
| 页面内 postcss 负担 | 每站全量 | 主进程 + 缓存复用 |
| 版本 bump | 手改 | 无（主进程独立） |
| 动态/内联覆盖 | ✅ | ✅（运行时兜底） |
| 容错 | ✅ | ✅（绝对容错） |
| `:has`/徽章/柱状图 | ✅ | ✅（运行时不动） |

**明确不提升**：`:has`/柱状图/徽章仍靠运行时——方案C修复版换不掉这个依赖，因为它是 DOM 操作。

---

## 主要风险与对策

1. **CSSOM 重复 / verbatim**：主进程转译后 verbatim（无需改）时，仍返回原文本，浏览器照常解析，无额外负担。拦截只是"经过主进程转发"，内容不变。
2. **首帧时序**：主进程转译是同步的（fetch 后立即 rewrite），浏览器收到的是改写后 CSS，首帧即到位。但 fetch 本身有网络往返 → 需主进程内存缓存（URL 内容哈希，现代站几乎不变）。
3. **CSP**：https 页仍需 `bypassCSP: true`。但容错保证即使被 CSP 拒绝，也退回原链接（方案A 的插入策略可复用），不崩站。
4. **非 `.css` 后缀 / `@import`**：拦截盲区仍存在 → 由页面世界运行时兜底（Fixer 精简版仍处理内联/动态）。

## 验证计划

- 单测：`isCss` 校验、rewrite 失败返回原文、`.css` 白名单匹配、loopback 排除。
- 冒烟：GitHub + ruffle.rs 真实加载，断言 CSSOM 规则数 > 阈值（修复前后对比，参照本次 `rules:3 → 6900`）。
- 手动：7k7k / 4399 旧站确认不崩（白名单 + 容错保证）。
- 三徽章/柱状图：确认运行时标记生效（回归脚本平台能力）。

---

## 结论

方案C修复版**能做**，但必须：
1. 主进程只做安全转译 + **绝对容错**（失败=原样放行，绝不丢表）。
2. `:has`/container 运行时**留在页面世界**，不拆 preload。
3. 拦截严格白名单，动态/内联由运行时兜底。

收益 = 首帧无 FOUC + 减平台负担；代价 = 多一套主进程转发 + preload 运行时保留。**收益是否值得取决于你有多在意 FOUC**。若 FOUC 可接受，方案A（脚本平台内优化）是更低风险的等价解。
