# ADR 0004：休眠与回收的优先级——游戏连续性 > 自动化可重复性 > 内存回收

- 状态：**已接受**（2026-11-25）
- 决策人：项目负责人
- 关系：**约束** [标签休眠报告](../reports/2026-11-24-tab-discard.md) 已交付实现的**触发条件**；回收手段（销毁 `WebContentsView`）不变
- 依据：`docs/agent-automation-architecture.md` §7（活动租约）、`app/src/main/activity-lease.ts`、`app/src/main/browser-window.ts` 的 `sweepDiscard()`

## 背景

`tab.discard = auto`（TTL 10 分钟）已上线，实测每标签回收 **≈111 MB**、唤醒 **120 ms**。但它的守卫链是按**普通网页**设计的：

```
非活动 ∧ 非内部页 ∧ 未置顶 ∧ 无租约 ∧ 未崩溃 ∧ 不出声 ∧ http(s) ∧ 后台超过 TTL  → 丢弃
```

对游戏页这条链有三处结构性错误：

1. **运行态只在内存里。** Flash/Ruffle 的 AVM 堆、`SharedObject` 待写缓冲、连接、计时器、帧循环，销毁视图即全部丢失。`SharedObject` 的异步写盘在进程被销毁时**不保证落盘**——丢的不只是"滚到哪一行"，可能是"打了几小时的存档"。
2. **"不出声"对游戏是噪声，不是信号。** 源码确认：静音**不会**让标签变成不出声（`content/browser/media/audio_stream_monitor.cc:66-68` 只看流状态；`web_contents_impl.cc:2742-2773` 的 `SetAudioMuted` 只在输出端 `SetMuted`，不动 `is_currently_audible_`）。所以"静音挂机"本来就被现有守卫挡住了。真正的洞是**静默期**：菜单、读条、回合制等待、纯 canvas 页面可以长时间没有音频，于是 `isCurrentlyAudible()==false` + 无人操作 + 超过 TTL → 正好被判成垃圾。
3. **自动化会让"长时间无人操作"变成常态。** M3 的 agent 常常是在等一个游戏内的回调/网络事件，TTL 类启发式会把这种"看起来没人用"的标签当成垃圾。

一句话：**内存回收是可放弃的收益，游戏/自动化被误杀是不可接受的事故。**

## 决策

### 1. 优先级（高的盖低的，不设例外开关）

**游戏连续性 > 自动化可重复性 > 内存回收。**

任何后续功能（内存压力触发、批量清理、Agent 主动省内存、多窗口合并）都不得用"更省内存"作为绕过下面门禁的理由。

### 2. 硬门禁：命中任何一条即**永久不休眠**（不是"延后"）

在现有守卫之上增加四条：

| 新增门禁 | 为什么 |
| --- | --- |
| **页面上有 Flash 内容**（`<embed>` / `<object>` / Ruffle 的 `<ruffle-player>`） | 见背景 1。**不能用引擎判定**：默认引擎就是 `ppapi`，拿它当判据会把所有标签都保护起来（实测已踩，见「后果」）。判定不了时**按"有"处理**（fail-closed） |
| **正在加载**（`contents.isLoading()`） | 现有守卫没有这一条；加载中被睡会连首屏都拿不回来 |
| **有自动化会话**（CDP/Agent 附着，含"只观察"） | 见背景 3；见第 4 条 |
| **`isCurrentlyAudible()` 不再单独作为判据** | 见背景 2：不出声 ≠ 没在用。对**含 Flash 内容的**标签，这一条不参与"可以睡"的判定（静音与否都不影响结论） |

保留现有守卫（非活动 / 非内部页 / 未置顶 / 无有效租约 / 未崩溃 / http(s) / 不出声）。注意最后一条的适用范围收窄如上。

### 3. 允许休眠的情况：必须**协作式**，且要有 ack

即便通过第 2 条（普通网页），丢弃前也要走一次"存盘握手"：

```
request → 页面侧 save（SharedObject.flush / Ruffle 的 save）
        → ack（上限 300 ms，可配）
        → 有 ack：销毁视图
        → 无 ack / 超时：放弃本次休眠（下一轮再试，不重试轰炸）
```

没有 ack 的丢弃一律视为 bug，不是"尽力而为"。

### 3b. 适用范围：只管**自动回收**，不管**显式动作**

`save → ack` 只约束"后台被自动睡掉"这一类**用户没在看着、也没有意图**的销毁。显式动作不在其列：

| 动作 | 是否要求 save → ack | 理由 |
| --- | --- | --- |
| 后台超时自动休眠 | **要** | 用户不在场、没有意图，丢的是他没保存的进度 |
| **手动切换引擎** | **不要**（2026-11-25 裁决） | 引擎切换**必然重建页面**：一个视图不可能同时承载原生插件与 Ruffle 运行时，所以"保持运行态"在这个动作里根本不成立。它是用户在看着、点下去、能看到页面重载的显式操作 |
| 关闭标签 | 不要 | 同上，显式且不可逆是用户预期的一部分 |
| 对象崩溃后的重建 | 不要 | 已经崩了，没有可保的运行时状态 |

判据可以压成一句：**"用户不在场的销毁"要走存盘握手，"用户在场的显式操作"不用**——
两者的共同点是都会丢运行时状态，区别是后者没有"用户不知道"这一层风险。

### 4. 自动化的额外要求：**全局闸**，不只是按标签租约

现有租约是**按 tabId** 的（`blocksDiscard(tabId)`）。这对 agent 不够：agent 可能正持有某个窗口/某个站点、或正在等待一个尚未绑定到具体标签的事件。

因此：

- 只要存在任何自动化会话（CDP 连接、agent 会话、workflow 运行中），**扫描器整体提前返回**，不做任何自动丢弃；
- agent 若确实需要省内存，必须**显式请求**（显式命令 + 显式目标标签 + 显式 reason），并在完成后自行承担重新加载的代价；
- `activity-lease.ts` 的 owner 表在接入 `agent` / `workflow` 时，除按标签登记外，**必须同时提供这个全局闸**。只加枚举值不加全局闸，等于给自己留一个只有线上才复现的坑。

### 5. 可观测：每一次"决定"都要留痕

`BAO_DISCARD_TRACE`（未设置时为空操作，与 `BAO_SELFHEAL_TRACE` 同款）：

```
[t] tab=7 engine=ppapi hasFlash=true audible=false muted=true loading=false
    leases=[user:keep-awake]  → 拒绝：hasFlash
[t] tab=3 engine=ruffle hasFlash=false audible=false loading=false
    leases=[]  → 休眠（save ack 41 ms）
```

理由必须落在**具体命中项**上，而不是一句"超时"。误杀时的第一个问题永远是"它为什么觉得可以睡"。

### 6. 内存压力不越过门禁

OS 的真实内存压力（`base::MemoryPressureMonitor`）**不改变**第 2/3/4 条：压力下也只允许 OS 自己换页/回收工作集，不允许因此丢掉一个在跑游戏的标签。这条明确写下来，是为了防止将来"内存告急"变成绕过门禁的理由。

## 后果

- **收益预期下调，且这是决策的一部分**：一个满屏 Flash 游戏的会话，回收量从"每标签 ≈111 MB"掉到 **0**。省内存退回到"用户主动关标签"，或将来由用户显式打开一个「允许休眠含 Flash 的标签」的开关（**默认关**，且打开后仍受第 3 条 `save → ack` 约束）。

### 批次 1 已落地（2026-11-25，2026-11-26 按审计修正）

改了 `app/src/main/browser-window.ts` 的 `sweepDiscard()`：新增 `isLoading()` 门禁、Flash 内容门禁、
`BAO_DISCARD_TRACE`，用例 `tab-discard.test.cjs` 现 **11/11**。

落地时踩到两个必须记下来的坑（都来自 2026-11-26 审计）：

1. **第一版用 `tab.engine === 'ppapi'` 当 Flash 判据**，结果全部标签都不休眠——本产品的默认引擎
   就是 `ppapi`（插件可用时每个标签都是它），"引擎是 ppapi" ≠ "装着 Flash"。trace 里普通页
   全是 `flash-content`，一眼就看得出来。
2. **第二版只探顶层文档、还按 URL 缓存阴性**，被审计复现两处漏判：页面可以**在首次探测之后**
   才插入播放器（懒加载 / SPA），而 `document.querySelector` 看不到 **iframe** 里的播放器
   （本产品的站点客户端 SWF 常挂在跨源 iframe 里，见 §6.5 的 surface 讨论）。

现在的实现（`flashContentOf()`）：

- **只在决策那一刻探**（TTL 到期才付这次 `executeJavaScript`）——早期阴性不可能被复用；
- **遍历整棵帧树**（`mainFrame.framesInSubtree` + 逐帧执行），跨源帧同样能判；
- **只粘阳性**，键是**绑定代际**（引擎切换提交 / 崩溃重建 / 唤醒后自动重探）；
- 判不出（帧已 detach / 执行失败 / 取不到主帧）按"有"处理（fail-closed）；
- 扫描器因此改成**异步且不可重入**（`sweepInFlight`），探测后、提交前重新校验视图身份
  （探测期间标签可能被切换/导航/重建）。

代价是每个**真要睡**的标签多一次跨帧 `executeJavaScript`（几毫秒）；够格被丢的时间点本来就稀少。
两条新用例（"迟插入的 Flash 内容"、"跨源 iframe 里的 Flash 内容"）**都在旧实现下实测失败**，
不是同义反复。

仍缺（批次 2，需另开一轮）：自动化会话级闸门、`save → ack`、`Ruffle` 侧在 preload 里主动上报
（这样连"决策时问一次"都省掉）。
- **需要新增的实现**（M2 收尾 / M3 前置）：
  1. ~~`tab.hasFlash` 探测~~ **批次 1 已用 DOM 探测替代**（见下）；
  2. `sweepDiscard()` 增补 `isLoading()` 与上式门禁；守卫链保持"单一函数、单一判定点"的既有形态；**批次 1 已完成**
  3. save/ack 协议（主进程 ↔ 页面 preload）；无 ack 不丢。
  4. 自动化全局闸 + `agent` / `workflow` lease owner。
  5. `BAO_DISCARD_TRACE`。**批次 1 已完成**
- **用例要求**（每条都要有，且必须能在隐藏并行下跑）：
  - 载入含 Flash 的页面 → 后台超过 TTL **不**休眠；
  - **静音**的 Flash 页后台超过 TTL **不**休眠（回归：静音不是判据）；
  - **长时间无音频**的 Flash 页后台超过 TTL **不**休眠（这才是原守卫真正的漏口）；
  - 加载中的普通页 **不**休眠；
  - 模拟自动化会话存在 → 所有标签 **不**休眠；
  - 普通页 → 仍按 TTL 休眠（防止"保护"把所有回收都吃掉）；
  - 无 ack 时丢弃被放弃，且标签仍可正常唤醒/交互。
- **与 B7 的关系**：本 ADR 是"为什么冻结档不做、为什么没有中间档"的正式答案。冻结档不释放内存（实测 0～+0.21 MiB）且会让 `executeJavaScript` 挂死，已经否决；真正的中间档只有"协作式 save + 丢弃"，而这需要第 3 条成立。
- **与 A4（多窗口共用外壳进程）的关系**：那条省的是每窗口 ≈70 MB 的**外壳**成本，与标签页的游戏状态无关，因此不受本 ADR 限制；但同样需要遵守第 4 条的自动化全局闸。
