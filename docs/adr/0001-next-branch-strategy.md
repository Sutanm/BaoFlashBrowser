# ADR 0001：BaoFlashBrowser Next 独立分支策略

- 状态：**已接受**（2026-11-15）
- 决策人：项目负责人
- 关联：`../specs/2026-11-14-electron138-flash-port.md`、`../specs/2026-11-15-forward-version-feasibility.md`
  ——这两个文件**在 `docs/port-138-140` 分支与 `next` 分支**，`main` 上不复制（同一事实不两处维护）
- 版本线口径：[`../version-lines.md`](../version-lines.md)（2026-11-23 定）

> **后续决策（2026-11-23 补记）**：本文「待定事项」4 项已全部结题——
> 1. 内核基线 = **Electron 39（v39.8.10）/ Chromium 142.0.7444.265**，非本文当时预想的 E37/138；
> 2. 前端栈 = **Vue 3 + Pinia**（详见 `next` 分支 ADR 0002 的 11-21 更新）；
> 3. Flash 策略 = 原生 PPAPI 为主、Ruffle 作回退，维持本文判断；
> 4. 首发功能集 = 按 `next` 分支架构讨论的 M0–M4 里程碑推进。
>
> 正文保持 2026-11-15 原样，不追改。

## 背景

1. 现产品基于 **Electron 11.5.0 / Chromium 87**（下称 **87 线**），是唯一已交付的 Flash 浏览器；
2. 研究线已证明：**自建 Electron 37 / Chromium 138 能跑原生 PPAPI Flash 并出帧**；140/142 可行，144 因 legacy IPC 消息系统整体移除而不可行（实测）；
3. 87 线与高版本内核在**渲染引擎、Node 版本、API、安全模型**上差异巨大（Chromium 87 → 138 跨 51 个里程碑，Node 12 → 22），把 87 的代码整体搬过去等于"把旧债带到新栈"。

## 决策

1. **新开分支 `next`**，产品代号 **BaoFlashBrowser Next**；
2. **87 线与 Next 线并行推进**：
   - 87 线：维护现状、修 bug、补 Flash 相关能力，**不追内核**；
   - Next 线：高版本内核，**所有技术选型与实现重新评估**，不受 87 现有架构约束；
3. **87 代码只作参考，不做完整移植或搬运**：
   - 允许"读 87 的实现以理解需求/踩坑"，但 Next 的模块需要按新栈重新设计、重新实现；
   - 不允许"整目录拷贝 + 改 import"式的迁移；
4. 文档、研究与构建资产（如自建 Electron 的工作流）**两条线共享**。

## 非目标

- 不把 87 的 `src/main/modules/**`、`src/webview-preload/**`、`src/renderer/**` 整体搬进 Next；
- 不在 Next 里保留 87 的历史兼容层（如为 Chromium 87 写的 polyfill、私有 scheme 方案），除非在新栈上重新论证必要；
- 不承诺 Next 与 87 功能一一对应——Next 的功能集按用户需求重新裁剪。

## 后果

| 方面 | 影响 |
| --- | --- |
| 代码 | Next 从空开始搭建（同仓库 `next` 分支 / 独立 worktree） |
| 构建与发布 | Next 独立打包、独立版本号、独立更新通道 |
| 需求 | 87 的功能清单只作为"需求参考表"，每项都要在 Next 里重新决定做不做、怎么做 |
| 风险 | 两条线并行，测试与发布流程需要分开；文档需要区分"87 行为"与"Next 行为" |

## 待定事项

1. Next 的内核基线：**E37/138（原生 PPAPI，已验证）** 还是 **E39/142（天花板，+2–4 周内核工作）**；
2. Next 的前端栈：React/Vite 沿用，还是重新选型（见 ADR 0002）；
3. Next 的 Flash 策略：单内核原生 PPAPI 为主，Ruffle 作为可选回退；
4. Next 的首发功能集（用户脚本、密码库、下载、截图、自动化等是否全部带入）。
