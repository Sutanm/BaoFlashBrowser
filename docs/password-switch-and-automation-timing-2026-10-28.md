# 换账号捕获与最小化点击时序排查（2026-10-28）

## 范围

用户反馈：7k7k 自动填充账号登录后，退出并登录另一个账号，首次不提示保存；最小化挂机时，设置 1100ms 的点击等待，实际间隔可能超过 2 秒。

使用 Windows 本机、项目锁定的 Electron 11、生产 BrowserView 预加载与本地 HTML 夹具测试。没有访问真实账号、修改真实密码库，未使用真实站点凭据。

## 1. 换账号捕获

### 复现

`tests/electron/fixtures/password-account-switch.html` 模拟单页 JSONP 登录：

1. 自动填充已保存的虚构账号 A。
2. 点击登录，动态插入脚本，并在脚本 onload 中完成登录。
3. 不导航，重新显示登录表单。
4. 输入虚构账号 B 并首次登录，检查主进程是否产生保存提示及待保存内容是否一致。

`18-password-account-switch` 使用真实 TabManager、捕获脚本、填充逻辑和 CDP binding；密码库仅由内存夹具替代。

修复前结果：A 登录后 debugger 已断开；第二次表单出现时未恢复捕获；B 的保存提示数为 0。

### 原因与修复

- JSONP 捕获后主动断开 debugger 是必要的，否则可能阻塞脚本 onload。
- 第二次登录框是页面内动态出现，未经过主文档加载周期；原来的表单检测只触发自动填充，没有重新启动捕获。
- 新表单/登录输入框获得焦点时，现在独立恢复捕获，不再依赖自动填充开关。
- 页面资源仍在加载时不重新附着，避免重新阻塞 JSONP。
- 捕获状态判断同时检查租约是否已释放，避免把自动填充短暂附着的 debugger 当成仍有效的捕获会话。
- MutationObserver 只为新密码输入框发出结构变化信号；登录期间普通 DOM 变化不重新附着。焦点检测保留，节流窗口内的新表单会延后补发信号。

修复后的本地回归结果：A 不重复提示；B 第一次登录提示 1 次；待保存凭据内容正确；JSONP onload 正常完成。真实 7k7k 仍需要用户使用新版构建确认。

## 2. 点击间隔

### 测量方法

- `automation-timing.html` 在真实 click/mousemove 事件中记录 `performance.now()`、`isTrusted`、页面可见性，同时记录 100ms 页面定时器及动画帧。
- `17-automation-timing` 分别测输入服务、截图加输入、完整积木执行链、完整 JavaScript 沙箱和真实 OpenCV 识图。
- `19-shell-automation-timing` 启动完整应用、临时用户目录，通过生产 IPC 创建并运行脚本，覆盖 React 外壳、TabManager、AutomationV3Service 和 BrowserView。
- 完整应用追踪每个 CDP 输入命令、视口查询、BrowserView bounds 更新及主进程定时器间隙。记录命令类型和时长，不记录任意脚本表达式或凭据。

### 修复前的证据

| 情况 | 测量结果 |
| --- | --- |
| 小型 BrowserView，前台坐标输入 | 约 1105～1116ms |
| 小型 BrowserView，最小化坐标输入 | 约 1107～1117ms |
| 完整积木执行链，最小化坐标点击 | 多数约 1150～1180ms |
| 真实 OpenCV，最小化稳定识图点击 | 约 1264～1309ms；引擎冷启动另有数秒开销 |
| 完整应用，最小化积木流程 | 一轮出现 1961ms；扩展测量出现额外 421ms 的 mouseMoved 命令 |
| 完整应用，最小化 JavaScript | 一轮出现 1786ms 间隔；单个 mouseMoved 达到 874ms，另有 639ms 停顿 |
| 隐藏整个窗口（与最小化不同） | CDP mouseMoved 可等待约 5000ms，点击间隔约 6110ms；截图也可超时 |

在记录到慢命令的完整应用样本中，视口查询没有超过 100ms，主进程 50ms 心跳没有超过 120ms 的间隙。额外停顿明确位于 `Input.dispatchMouseEvent(mouseMoved)` 的应答等待，而不是 `sleep(1100)` 被普遍节流。

BrowserView 保持后台定时器运行，并不保证这个 CDP 鼠标移动应答能及时返回。保留 capturer 或关闭宿主后台节流的对照也没有解决隐藏窗口问题。

### 修复与结果

不按住按钮的鼠标移动改用 `webContents.sendInputEvent(mouseMove)`，避开 CDP 鼠标移动的画面帧应答等待。点击按下/松开、拖拽中按住按钮的移动仍使用 CDP；坐标转换、取消检查、租约释放和拖拽释放保持原有约束。

先在完整应用中替换输入端口做对照，通过后修改生产输入服务；随后关闭测试替换，直接测试生产代码。最新一轮每组 10 次点击：

| 完整应用场景 | 9 个相邻点击间隔范围 | 可信移动 / 点击 |
| --- | --- | --- |
| 前台积木流程 | 1153～1171ms | 全部通过 |
| 前台 JavaScript | 1135～1144ms | 全部通过 |
| 最小化积木流程 | 1150～1175ms | 全部通过 |
| 最小化 JavaScript | 1136～1149ms | 全部通过 |

40 次点击全部收到，无超过 100ms 的 CDP 按钮输入命令，没有复现先前的鼠标移动应答停顿。该短期结果不等于所有游戏的长期性能保证。

**1100ms 是两步之间的等待时长，不是固定点击周期。** 实际间隔还包含视口确认、输入处理，以及脚本中的截图/识别等工作。修复没有把循环偷偷改成固定频率，也没有让迟到操作集中补发。

## 复跑

### 后续：其他输入路径实测

在完整应用中，通过生产 JavaScript API，每种操作前台/最小化各执行 10 次；页面记录实际事件及 `isTrusted`，主进程继续记录 CDP 耗时。

| 操作 | 前台耗时范围 | 最小化耗时范围 | 本轮结论 |
| --- | --- | --- | --- |
| 普通移动 | 30～49ms | 32～39ms | 没有同类长停顿，包含视口检查开销 |
| 点击输入框 | 32～51ms | 29～48ms | 没有同类长停顿 |
| 拖拽（配置 80ms） | 136～206ms | 189～986ms | 确认仍有问题；一条按住按钮的 CDP mouseMoved 耗时 794ms |
| 滚轮 | 1～5ms | 1～4ms | 没有同类长停顿 |
| 按键（含按下、字符、松开） | 3～10ms | 3～12ms | 没有同类长停顿 |
| Ctrl+A | 1～5ms | 1～4ms | 没有同类长停顿 |
| 整段输入 | 2～5ms | 1～7ms | 没有同类长停顿 |
| 两字符逐字输入（20ms） | 52～68ms | 60～71ms | 包含逐字等待，没有同类长停顿 |

拖拽开始前的普通移动已经修复，但按住按钮后的中间移动仍使用 CDP mouseMoved，因而仍可能等待画面帧。此次测试确认该问题，尚未更改按住按钮移动的实现。

此外，拖拽配置的 80ms 目前只是分段 sleep 的总量，每段 CDP 命令耗时会继续叠加，因此前台也明显超过 80ms。即使解决最小化应答停顿，仍需单独检查拖拽的总时长调度语义。

两种窗口状态均收到 50 次带左键按住状态的移动、20 次按下/松开、10 次滚轮和对应键盘/文本事件，记录的事件均为可信事件。此结论覆盖本地 HTML 和本次 Windows 环境，不代表所有 SWF 或长期运行场景均已验收。此次新增测量没有修改产品输入代码。

### 拖拽修复后的复测

后续已修复上述拖拽问题：按住按钮的中间移动也使用原生可信 mouseMove，明确传递 `leftButtonDown` / `middleButtonDown` / `rightButtonDown`，按下和最终松开仍使用 CDP。

移动阶段以 `performance.now()` 的统一起点和截止时间调度，不再逐段叠加命令处理耗时；如果一次等待已经超过后续中间点的截止时间，跳过过时中间点，最终仍到达终点。取消时仍进入 finally 松开按钮并释放租约。

最新完整应用回归，前台与最小化各 10 次 80ms 拖拽：

| 测量 | 前台 | 最小化 |
| --- | --- | --- |
| 整次 API 调用（含视口确认和输入开销） | 117～127ms | 122～126ms |
| 页面实际按下到松开 | 80.6～93.3ms | 90.1～93.5ms |

未出现之前约 794ms 的 CDP 中间移动停顿；没有超过 100ms 的 CDP 输入命令。所有采集事件仍为可信事件，拖拽移动携带按住状态，按下/松开数量一致。由于系统调度和事件投递开销，80ms 不能视为实时系统的硬性截止保证。

783 项单元测试、三层类型检查、lint 通过，主进程已重建；最小化 PPAPI/Ruffle 100% 比例输入冒烟也通过。新增单元回归覆盖绝对时间调度、迟到时跳过中间点、拖拽中取消释放及中/右键状态。没有重新声称已验证任意真实游戏的拖拽逻辑。
