# 颜色定位 POC 阶段报告

> 日期：2026-09-04
> 状态：POC 已接入 Automation Core、助手与测试中心；真实困难负样本暴露误报，自动路由仍属实验能力

## 1. 本批目标

验证颜色定位能否直接处理 BaoFlashBrowser 捕获链路使用的 BGRA 内存帧，并与现有 OpenCV 在同一素材、同一场景和同一缩放集合下对照。第一批不追求完成产品接入，重点验证：

- 是否能自动从普通 PNG 提取背景、主体颜色和特征点；
- 是否能处理透明素材、纯色背景素材和水平镜像；
- 是否能拒绝不含目标的场景；
- 候选唯一性是否足以成为硬判定条件；
- 性能是否有继续优化的价值。

## 2. 已完成

- 新增纯 BGRA 多点颜色匹配器，不依赖 Sharp、DOM、Electron 或 OpenCV；
- 自动识别占主导的边框背景色并从特征中排除；
- 自动选择场景中相对稀有的颜色作为候选锚；
- 支持多缩放、水平镜像、ROI、候选去重；
- 评分同时考虑固定几何点和窗口内主色组成；
- 增加合成测试，覆盖不透明背景、透明镜像和不可判别模板；
- 增加可重复执行的真实素材对照命令：`npm run benchmark:vision:color-poc`。

## 3. 第一批结果

测试环境为当前 Windows 开发机，5 次热运行，颜色阈值 0.35；“接受”条件暂定为最高分 ≥0.55 且最高与第二独立候选差值 ≥0.08。

| 场景 | 颜色定位 | 唯一性 | OpenCV 最强候选 | 结论 |
|---|---:|---:|---:|---|
| 2132×1253 场景中的鱼 | 0.801 | 0.004 | 0.994（错误位置） | 找到目标附近，但多个局部候选近似同分，正确拒绝硬判定 |
| 1422×828 游戏画面中的鱼 | 0.869 | 0.001 | 0.994（错误位置） | 找到鱼，但缩放候选未聚合，暂不应对用户声称成功 |
| 1418×839 鱼负样本 | 无 ≥0.35 候选 | — | 0.993（错误位置） | 颜色策略成功拒绝；OpenCV alpha 小尺度候选分数失真 |
| 1422×828 鱼钩场景 | 0.883 | 0.002 | 0.989（错误位置） | 找到鱼钩附近，但不唯一 |
| 1418×839 鱼钩负样本 | 0.776 | 0.006 | 0.989（错误位置） | 验证了“小目标常见颜色不可单帧可靠判定”的研究结论 |

热运行 p95 观察值：

- 鱼：颜色定位约 70–370ms，OpenCV 约 640–1500ms；
- 鱼钩：颜色定位约 770–850ms，OpenCV 约 270–320ms；
- 颜色定位并非天然更快。目标越小、锚颜色越常见，候选越多，当前纯 JS 验证成本会显著上升。

这些数字仅用于 POC 路线选择，尚不是产品性能承诺。

## 4. 已确认的架构结论

1. 颜色定位适合作为 `ImageLocator` 的匹配策略，不应成为新的动作或新的坐标体系。
2. 不能只用最高分；最高候选与第二个独立空间候选的差值必须进入判定。
3. 多缩放产生的同一实体候选必须先做“对象级聚类”，再计算唯一性。当前按小框重叠去重不足。
4. ROI 是性能和准确率硬条件，特别是鱼钩等小目标；全游戏区域暴力扫描不可作为最终实现。
5. 当前 OpenCV 的 alpha + 小尺度候选可在错误位置给出接近 1.0 的分数，颜色策略有实际补位价值，但不能全面替代 OpenCV。
6. 原研究中效果最好的算法实质是“颜色组成窗口匹配”，不是传统固定 N 点全中。本 POC 已验证两者需要融合。

## 5. 第一批当时规划

1. 建立量化的对象级候选聚类，避免同一条鱼的多个缩放/局部框互相压低唯一性。
2. 把场景颜色扫描改为单遍索引并缓存模板签名，降低重复全帧扫描。
3. 增加水面 ROI 对照，目标是鱼类场景 p95 不高于 50ms。
4. 从视频抽帧中建立连续帧正样本和无鱼负样本，不依赖单张截图下结论。
5. 只有达到召回率、误报率、唯一性和耗时门槛后，才增加 `method: 'color'` 并接入 Core。

## 6. 第一批当时决策

继续 POC，但不接入用户可见功能。第一批已经证明颜色信息有价值，同时也证明“直接把旧式多点找色做成积木”会产生错误承诺。下一批必须先解决对象聚类、ROI 和连续帧基准。

## 7. 第二批：空间覆盖、聚类与连续帧

第二批没有扩大用户界面，而是修正第一批暴露出的评分和性能问题：

- 素材签名改成“每种主色 + 各自的空间点集”，不再只比较窗口内颜色总量；
- 同一实体在不同缩放、镜像和局部位置产生的候选先按对象聚类，再计算第一、第二独立候选差值；
- 素材签名可复用，连续识别不再每帧重新分析 PNG；
- 场景先建立量化颜色直方图，只扫描最稀有且实际存在的锚颜色；
- 固定特征先做廉价预筛选，每个缩放最多对 48 个候选计算完整颜色覆盖；
- 增加 ROI 坐标保持、签名复用和“局部同色块不能冒充完整目标”的单元测试；
- 增加 `npm run benchmark:vision:color-video-poc` 连续帧基准。

静态真实素材（2 次热运行、颜色候选阈值 0.35）的代表结果：

| 场景 | 最高分 / 独立候选差 | p95 | 结果 |
|---|---:|---:|---|
| 1422×828 鱼，全游戏区域 | 0.598 / 0.204 | 220ms | 接受，位置稳定在目标附近 |
| 同一帧，180×150 ROI | 0.598 / 0.120 | 101ms | 分数与位置不变，耗时下降约 54% |
| 1418×839 鱼负样本 | 无 ≥0.35 候选 | 192ms | 正确拒绝 |
| 1422×828 鱼钩，全游戏区域 | 0.774 / 0.294 | 635ms | 接受 |
| 同一帧，160×150 ROI | 0.774 / 0.294 | 12ms | 分数与位置不变，耗时下降约 98% |
| 1418×839 鱼钩负样本 | 无 ≥0.35 候选 | 549ms | 正确拒绝 |

对象聚类解决了第一批“同一目标的多个缩放候选互相压低唯一性”的主要问题。候选预筛选使鱼全画面约从 612ms 降至 220ms，鱼钩全画面约从 1.75s 降至 635ms；但全画面小目标仍不够快，ROI 仍是产品化硬条件。

连续帧使用 188 张 1418×842 原始帧，在 550×380 水面 ROI 内逐帧运行：

- p50 约 11.7ms，p95 约 21.8ms；
- 目标运动区间为第 45–111 帧，共 67 帧；其中 65 帧达到暂定接受条件，2 帧因独立候选差不足而拒绝；
- 接受轨迹最大单帧跳动约 14px；
- 第 1–44 帧与第 112–188 帧均未达到接受条件。

这一组数据证明颜色定位适合 ROI 内的连续监测和轨迹补强。不过，同一素材在静态截图中的分数约 0.60，在视频帧中的分数约 0.30，说明缩放、采样或捕获来源会显著影响绝对分数。第二批不能据此引入一个面向所有素材的全局阈值。

## 8. 第二批结论与下一门槛

当前路线从“值得研究”提升为“可作为 OpenCV 的候选补强和连续追踪器”，但仍不应直接成为默认识图器。接入 Core 前还需要：

1. 把颜色分数归一化到不同捕获缩放下可比较，或为素材生成自动校准信息；
2. 用首帧定位后的动态小 ROI 做连续追踪，避免每帧扫描固定大区域；
3. 明确与 OpenCV 的组合策略：OpenCV/颜色任一召回后，使用另一策略复核，而不是向普通用户暴露两套参数；
4. 用更多素材包建立正负样本，确认 48 候选预筛选不会损失召回；
5. 达到门槛后再实现 `ImageLocator` 内部策略，Blockly 仍只显示“识别图片”，不增加“多点取色”专业积木。

## 9. 第三批：连续追踪与鱼钩事件门槛（2026-09-05）

本批没有把实验参数暴露给普通用户，也没有直接改变 `ImageLocator` 的执行语义。先增加两类可复用基础能力：

- `ColorPointTracker`：首帧在指定 ROI 定位，命中后围绕上一帧动态缩小 ROI；连续局部丢失达到预算后才回到初始 ROI 重捕获。接受判定同时要求最低分和独立候选差，避免相似色块冒充目标。
- `ColorColumnTracker`：在稳定的横向列附近追踪特定颜色组的纵向信号。它适合玩家静止、鱼钩列稳定的钓鱼阶段；同色像素出现在列外时不会参与候选。

真实帧结果：

| 场景 | 帧数 | 结果 | 性能 |
|---|---:|---|---:|
| 鱼，1418×842 完整录像帧，动态 ROI | 188 | 运动区间 67 帧中接受 65 帧；最大单帧跳动约 14px；目标消失区间全部拒绝 | p50 约 7.6ms，p95 约 13.0ms |
| 鱼钩，290×208 局部录像帧，固定钩列 | 115 | 应存在的 1–86 帧检出 86/86；消失后的 89–115 帧误报 0/27 | p50 约 0.07ms，p95 约 0.18ms |

鱼钩门槛可用 `npm run benchmark:vision:fishing-hook` 重跑。它会在召回率低于 98%、消失区间出现误报或 p95 超过 5ms 时失败，并将逐帧结果写入 `.cache/vision-benchmark/`。

结论更新：鱼钩不适合作为全画面通用图片做暴力搜索，但“玩家/面板锚定 → 固定钩列 → 小 ROI 颜色事件追踪”已经通过当前真实录像门槛。下一阶段应把它作为 Core 内部的连续追踪能力接入；在跨缩放分数归一化和更多负样本完成前，不把颜色匹配直接设为所有图片定位的默认替代算法。

## 10. 第四批：Core 显式策略与独立 Worker（2026-09-05）

本批把通用颜色定位接入 Automation Core，但保持默认行为稳定：

- `ImageLocator.method` 支持 `template | color | auto`；生产会话字段省略时当前会进入自动路由，显式 `template` 可固定原 OpenCV 模板匹配。后续真实困难负样本证明 `auto` 仍需结构复核，不能称为安全路由。
- JavaScript Capability Broker 对该字段做白名单校验，未知策略在进入 Host 前拒绝。
- 颜色匹配运行在独立 `worker_threads` Worker，不占用 Electron 主线程；素材签名在 Worker 内按 `cacheKey` 复用。
- ROI 在发送 Worker 前裁剪，返回坐标再映射回捕获帧坐标。
- Worker 启动、单次请求和取消均有失败边界；异常后清理请求与素材缓存，可在下次调用重建。
- 完整自动化包携带 `color-vision-worker.cjs`，无自动化 win32 包明确不携带 OpenCV/颜色 Worker。

合成 Worker 门禁验证了完整画面与 ROI 路径均能返回同一目标坐标；ROI 场景传输量从 38,400 bytes 降至 4,800 bytes。该数字仅证明协议、裁剪和坐标回填正确，不代表真实素材性能。

本节记录的是第四批当时的保守策略。后续跨缩放、负样本、自动路由及 Core/助手/测试中心等价性门禁均已完成；当前结论以第十二节为准。普通 Blockly 图片积木仍不出现算法参数，但其生产执行路径已在内部使用自动路由。

## 11. 第五批：跨缩放置信度校准（2026-09-05）

新增 `npm run benchmark:vision:color-scale`，以同一真实鱼素材验证 0.75×、1×、1.25× 场景，并分别覆盖最近邻与平滑插值。测试使用素材 Surface 元数据推导的窄尺度邻域，避免把明显不可能的小尺度候选混入唯一性判定。

颜色匹配器的原始分数继续表示 RGB/几何质量；Core 对外置信度改由“原始质量 + 与第二独立候选的差值”校准。候选缺失时按内部采集下限 0.2 计算保守差值，不能把弱而孤立的噪点当成绝对唯一。

结果：

- 最近邻和平滑插值的三档缩放均以用户阈值 0.9 通过，位置误差约 6.5–10.7px；
- 校准后的三档置信度一致，避免窗口缩放后仅因插值导致阈值突然失效；
- 鱼负样本置信度约 0.273，拒绝；
- 鱼钩负样本原始最高分约 0.503，但与第二候选只差约 0.006，校准置信度约 0.527，拒绝；
- 重复同强度目标仍由 0.08 唯一性门拒绝。

该校准只用于颜色路径，不会改变 OpenCV 模板匹配分数。它解决了颜色策略接入 Core 后默认 90% 阈值无法跨缩放使用的问题；自动路由通过门禁后，普通 Blockly 已可在不暴露算法概念的情况下使用该能力。

## 12. 第六批：自动路由 POC 与透明边界坐标（2026-09-05）

新增 `npm run benchmark:vision:routing-poc`，把真实游戏素材与生成的普通 UI 控件放在同一个路由矩阵中。临时策略为：颜色签名可用时由颜色唯一性判定；素材不具备可区分颜色时回退 OpenCV。该策略后来被真实页面中的“同色异形”负样本证明不够安全。

当前源码包含 20 个用例（15 个真实、5 个生成）。2026-09-06 使用当前工作区复跑结果为：

- 单用 OpenCV 判对 14/20，主要问题是小尺度 alpha 高分误报和相邻动画帧召回不足；
- 单用颜色策略判对 15/20；
- 路由策略判对 20/20；结果产物为 `.cache/vision-benchmark/routing-poc-2026-09-06T01-50-22-497Z.json`；
- 缓存中另有旧版 25 用例的 15/25、21/25、25/25 结果，但当前基准源码和判定门已经变化，该历史结果不可作为当前门禁；
- 完整钓鱼场景中的鱼原始分数约 0.50，但相对第二独立候选领先约 0.13，经归一化唯一性校准后达到 0.9 门槛；
- 透明或实色背景被签名提取裁掉后，现在会把素材原始边界偏移加回结果，与 OpenCV 一样返回完整素材矩形，避免点击中心偏移。

路由策略已封装为 `AutomaticVisionMatcher`，并由上述基准直接调用生产路由器、颜色 Worker 与 OpenCV Worker，不再由基准手工模拟决策。`ImageLocator.method: 'auto'` 可供 Core/JavaScript 显式试用；图片组会一次分出不支持颜色签名的成员，仅对这些成员回退 OpenCV。颜色 Worker 超时或崩溃会原样上报，不会被伪装成 OpenCV 成功；作者“最强候选”仍保留 OpenCV 黄框语义。

助手、测试中心与脚本 Runtime 现已共用同一组常驻 OpenCV/颜色 Worker 和同一个自动路由策略。三者先按用户真实阈值执行 Core 判定；未通过时，作者工具再单独调用 OpenCV 获取黄色最强候选。黄色候选只负责解释“差多少”，不会因为自身分数高于阈值而覆盖自动路由的拒绝结论。

## 13. 第七批：生产路径统一验收（2026-09-05）

- Runtime、助手和测试中心共享模板 provider、OpenCV Worker、颜色 Worker 与 `AutomaticVisionMatcher`，不再各自创建不同识别器。
- 两个 Worker 随 Automation Vision 一起预热；会话关闭时只释放自身拥有的资源，不会误关共享 Worker。
- 普通 Blockly 与省略 `method` 的脚本在生产会话中默认走 `auto`；显式 `template`、`color`、`auto` 均保留。
- 作者工具采用“真实自动判定 → OpenCV 黄色诊断”两段式；新增回归测试验证一个高分黄色候选仍保持 `matched=false`。
- 自动路由当前源码复跑为 20/20；颜色 Worker 的分项门禁和当前小语料通过不等于生产安全。人物状态栏、树叶、收线局部等真实困难负样本尚未进入门禁，不能据此宣布默认路由安全。
- 完整 TypeScript 检查通过；111 个单元测试文件共 669 项通过；3 个集成测试文件共 19 项通过；Lint 为 0 error、34 个仓库既有 warning；生产构建同时产出 `vision-worker.cjs` 与 `color-vision-worker.cjs`。

真实 Electron 页面复核已经发现同色异形误报：人物素材可命中状态栏/详情面板，鱼钩素材可命中树叶或收线局部。下一步必须把这些画面加入带 ground truth 的回归语料，并把自动路由升级为“候选生成 + 结构验证”；在此之前 `auto` 仍按实验能力管理。

## 14. 第八批：颜色提案与局部结构复核（2026-09-06）

生产颜色 Worker 已不再直接把稀疏特征色分数作为最终结果。它保留同位置的多倍率候选，并以完整素材像素复核颜色覆盖、轮廓纯度、轮廓 IoU、色彩排列及边缘结构；只有结构分和独立候选差同时通过才会返回可执行命中。作者诊断中的同色异形候选显示结构证据，不再被唯一性加成显示为 100%。灰度或缺乏色彩区分度的素材在能力分类阶段直接交给 OpenCV。

新的 `npm run benchmark:vision:structure` 覆盖日/夜鱼钩、状态栏/树和无鱼钩困难负样本；`npm run benchmark:vision:fishing-hook` 直接调用生产 Worker 验证连续帧。当前结果：鱼钩存在 86/86、消失后误报 0/27、p50 约 16.4ms、p95 约 27.7ms；自动路由矩阵 20/20。完整单元测试为 113 个文件、684 项，集成测试 19 项，TypeScript 检查与生产构建通过。

剩余风险是首次全屏、多倍率提案仍慢，且真实困难语料数量有限。下一批应优先复用已学习 scale 和已确认位置形成 ROI，再做连续跟踪与丢失重捕获；不能以当前样本结果宣称所有小目标均已解决。

## 15. 第九批：模板预编译与帧索引复用（2026-09-06）

自动化包注册后会在共享调度器中后台解码最多 64 个图片素材，并提前把颜色签名编译进常驻 Worker；不支持颜色签名的灰度素材仍保留给 OpenCV 路由。颜色 Worker 对每个请求只建立一次量化场景索引，图片组成员共享该索引；同一 `frameId`、同一区域的后续倍率回退或重复查询直接复用 Worker 内的帧和索引，不再重复传输 BGRA。

`benchmark:vision:color-worker` 已覆盖预编译、灰度分流和同帧复用：合成全帧首次匹配约 7.1ms，同帧第二次约 2.8ms，第二次传输量为 0。真实鱼钩连续帧仍为存在 86/86、消失后误报 0/27，p50 约 16.6ms、p95 约 24.8ms。单素材首次全屏搜索仍受候选生成支配；本批主要收益面向图片组、回退倍率和重复查询，下一步再以真实游戏测量首次全屏端到端耗时。

## 16. 第十批：图片组双 Worker 并行（2026-09-06）

真实 8 图全屏基准证明主要耗时来自“素材 × 多倍率”的候选生成，而不是场景索引。生产匹配器现按 CPU 数量启用最多 7 个常驻颜色 Worker，图片组通过共享任务队列由空闲 Worker 领取完整素材；每个素材的全部倍率始终留在同一 Worker 内完成提案、结构复核和候选差判定。曾验证过按倍率分片，但它会改变素材内部候选竞争并令鱼钩连续帧由 86/86 降为 84/86，因此没有采用。

新增 `npm run benchmark:vision:color-group`，以 8 个真实钓鱼素材和日间完整场景同时比较分组与逐图结果。动态 7 路调度实测约 0.90～1.45s，空闲机器多次进入 1s；相对约 3.52s 的原始串行基线提升约 59%～74%。所有 Worker 共享一份只读 BGRA 帧，预热素材分散缓存，避免把每张素材复制 7 份；场景索引也由 Map 数组改为 4096 桶 CSR，单次构建由约 62ms 降至约 16ms。门禁逐项核对素材、坐标、倍率、分数及不支持列表，分组结果与逐图串行完全一致。单图继续走原始单 Worker 路径，鱼钩门禁保持存在 86/86、消失后误报 0/27，p50 约 15.7ms、p95 约 22.6ms。
