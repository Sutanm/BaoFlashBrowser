# 飞窗合并为单一叠加层视图

2026-11-24 · 起因：飞窗点击有延迟、预热效果不好，且「才两个飞窗就得错开预热时间」。

## 1. 原来的架构与实测

每种飞窗一个 `WebContentsView`，各自加载 `index.html?baoOverlay=<kind>`：

| 测量项 | 数值 |
| --- | --- |
| 第一次打开（预热前） | **260 ms** |
| 预热后打开 | 22 ms |
| 单个标签页的渲染进程 | **4 个**（外壳、页面、quick、panel） |
| 预热排期 | quick 600 ms、panel 1200 ms（**必须错开**） |

根因：`new WebContentsView()` 会**新起一个渲染进程**（Electron 实测资料：30–90 ms 建进程，
再加文档加载与首帧）。飞窗越多，预热排期越长，进程也越多。

## 2. 改法：一个飞窗视图 + 内容切换

| 项 | 改后 |
| --- | --- |
| 飞窗视图 | **1 个**（`?baoOverlay=overlay`），panel 与 quick 共用 |
| 渲染进程（单标签页） | 4 → **3** |
| 预热 | **一次**（外壳 `loadURL` 完成后立刻建），不再错开 |
| 切换 panel ↔ quick | 同一文档内 `v-show` 切换组件，毫秒级，不重新加载 |
| toast | 保持独立视图（它出现在页面任意位置，尺寸/生命周期不同） |

实现要点：

- `shell-overlays.ts`：`flyout`（共用）+ `toastItem` 两个视图；`sender()` 根据文档模式 `overlay`
  与当前内容类型判定角色（所以 `resize-quick` 仍只接受「正在显示 quick」时的调用）；
- `OverlayHost.vue`：两个组件都常驻挂载、`v-show` 切换，靠 `panel-opened` / `quick-opened`
  事件决定显示哪个；
- 两个组件用 `defineAsyncComponent` 懒加载：叠加层文档首帧只含宿主，主题开关那 256 kB 的
  插画在后台并行加载，不阻塞第一次打开。

## 3. 实测（同一台机器，真实窗口）

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| 预热完成后打开 quick | 22 ms | **20–24 ms** |
| 预热完成后打开 panel | 24 ms | **23–28 ms** |
| 窗口出现后立刻点（≤150 ms，预热还没跑完） | 260 ms | 160–290 ms（三次：291 / 216 / 160） |
| 飞窗视图数 | 2 | **1** |
| 预热次数 / 是否需要错开 | 2 次、需要错开 | **1 次、不需要** |

说明：冷启动那一栏是「窗口刚出现、预热视图的渲染进程还在建」的极端情况。真实使用里用户
从看到窗口到点齿轮远超 150 ms，所以实际体验是 20–25 ms 那一档；而改前**每个**飞窗冷启动
都是 260 ms，且要按 600/1200 ms 排期预热。

## 5. 未做 / 下一步

- toast 还没并入共用视图（它的定位规则不同，需要单独确认是否值得）。
- 冷启动那一档仍受「建渲染进程」限制；如果要彻底消除，就得让飞窗视图在**窗口创建前**就存在，
  代价是启动时多一个渲染进程（在没有窗口时也要建），需要权衡。
- 更彻底的方案是「原生 `Menu.popup` 做引擎下拉」——零渲染成本，但无法自绘主题开关。

## 6. 修正节（2026-11-25 22:40 追加）

本文的数字属于**共享进程之前**的方案：那时 panel/quick/toast 已合并为一个视图，但仍是独立渲染进程，
所以"预热后 20–25 ms""窗口出现后立刻点 260 ms"都还成立。之后的做法与数字：

| 项 | 本文（单视图 + 独立进程） | 现在（单视图 + 共享外壳进程 + 常驻预热） |
| --- | --- | --- |
| 首次打开（无预热） | 160–290 ms | 常驻档默认：**3–10 ms**；`never` 档约 144 ms 端到端 |
| 预热后打开 | 20–25 ms | 3 ms（`visible`），content 6–12 ms |
| 常驻成本 | 一份独立渲染进程（69–72 MB） | **+6 MB**（文档活在外壳进程里，渲染进程数不变） |
| 视图隐藏后重显 | 当时估"需重建合成面" | 实测 **3 ms**，不需要任何 keepalive/占位 |

本文 §5 的两条"下一步"（toast 并入共用视图、冷启动受建进程限制）现在的状态：toast 已并入同一个文档；
"让飞窗视图在窗口创建前就存在"这条已经以共享进程 + 常驻预热的方式实现了，代价从一份渲染进程降到 +6 MB。
详见 [overlay-shared-process-demo.md](../discussions/2026-11-25-overlay-shared-process-demo.md) §5–§7。
