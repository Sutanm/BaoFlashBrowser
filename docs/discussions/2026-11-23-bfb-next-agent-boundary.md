# Agent 能力边界与反需求

2026-11-23 · 讨论记录（未审计）

由三轮讨论整理：①Tabbit 对比中「哪些是他们能做、我们不能、但我们可实现且值得实现」；②由此反向得到的「哪些不该做」；③用户追问「我们的浏览器放权已经很厉害（CDP + 自动化 API 几乎能拿到所有信息），为什么不放得更开」。结论尚未回填 F 区，审计通过后并入 [架构 §F3](2026-11-21-bfb-next-architecture.md) 的补充条款，或独立成 F9 反需求清单。

本文不修改任何已定合同。与 [F8 决策层实现选型](2026-11-21-bfb-next-architecture.md) 并列：F8 管「决策层用谁」，本文管「工具面开到哪、哪条腿不能接」。

## 0. 结论摘要

| 判断 | 内容 |
| --- | --- |
| 三类「不做」性质不同 | A 结构性红线（永不）/ B 定位冲突（改定位才谈）/ C 负 ROI（有触发条件） |
| 放权的正确方向 | **能力继续加（加工具、加视觉原语），入口与方向一步不放**（不加原始通道、不加无审批外发） |
| 核心判据 | **0→1 是性质跃变，1→2 是量的扩张**；只做 1→2 |
| 反直觉结论 | CDP 大而不危险（不可被页面内容驱动、缺 egress）；`page.fetch` 小而危险（正是可被页面内容驱动的 egress） |
| 必须承认的边界 | 观察内容进模型上下文＝第二条出境腿，无法消除，只能压低 |

## 1. 三类「不做」

| 类 | 含义 | 条目 | 能否翻案 |
| --- | --- | --- | --- |
| **A 结构性红线** | 做了就是拆自己的防线，与实现质量无关 | ① 带 cookie 的特权 fetch ② 桌面 UIA 控制第三方应用 | 永不（除非改产品定义） |
| **B 定位冲突** | 技术上都能做，做了就是在别人的战场上用更少资源打 | ③ 通用问答/深度研究/文档生成 ④ 85 条电商社交网页配方 | 改定位才谈 |
| **C 负 ROI** | 对主场景无用，却要付长期成本 | ⑤ `chrome.*` 历史/书签/阅读列表数据面 | 有触发条件 |

## 2. 逐项记录

每项六个字段：能力 / 诱因 / 拒绝理由 / 不做的代价 / 解冻触发条件。

### 2.1 带 cookie 的特权 fetch（Tabbit 的 `page.fetch`）

- **能力**：在浏览器上下文内发任意请求，携带用户登录态 cookie，返回值直接进模型上下文。
- **诱因**：接口返回结构化 JSON，比点 DOM 干净十倍；做通用助手几乎必然要加。
- **拒绝理由**：
  1. 重新接上 lethal trifecta 的第三条腿。F3 的现有姿态是「唯一外发工具（`GM_xmlhttpRequest` 等价面）挂 sensitive 审批」，挂机无人值守时等于关闭；一旦加上默认可用的 fetch，页面里一句隐藏文本即可完成「私有数据 → 攻击者域」。
  2. 危险点在于「看起来无害」——它不是 `getCookies()` 那种一眼像权限的能力，评审时最容易被放过。
  3. 我方不存在该需求：CDP 操作页面时登录态自动带上，**不需要「读 cookie」这个能力，只需要「带登录态操作」这个效果**，后者天生就有；前者只增加泄漏面。
- **不做的代价**：纯抓取类任务退化为多步 DOM 抽取，慢一点、贵一点。
- **解冻条件**：M4 通用助手真立项，且先具备「目标域白名单 + 每次调用审计 + 结果不进模型上下文」三件套。

### 2.2 桌面 UIA 控制第三方 AI 应用

- **能力**：用 Windows UIA（PowerShell `-NoProfile -NonInteractive -STA`）找到 Cursor / WorkBuddy / Codex 窗口，填入任务、发送、读回回复。Tabbit 以 `agent-windows-uia.ps1` + `agent-*-desktop.mjs` 实现，并有 `host_integration.*_installed` 探测。
- **诱因**：零成本「借用」用户已付费的 AI 能力。
- **拒绝理由**：
  1. 不可测试：依赖窗口标题、控件树、语言、DPI、版本；一次小版本更新即静默失效，或更糟——发错窗口。
  2. 不可审计：无法证明「发了什么给谁」，与「每条动作可回放」路线直接冲突。
  3. 版本组合 O(n²)：Codex × Claude Code × Cursor × WorkBuddy × 各自版本。
  4. **结构原因**：Tabbit 需要点桌面，是因为它在浏览器内没有特权工具面，只能用 Playwright 从外部点；我们在浏览器内有工具面，绝大多数任务自己就能完成，该需求在本架构中不存在。
- **不做的代价**：「让 Codex 顺手改代码」这类跨应用任务没有；替代方案是 A2 裸连接（检测到 CLI 即以协议直连，不做 UI 自动化）。
- **解冻条件**：永不进主包。真要做，做成用户显式安装的独立插件，与发行包解耦。

### 2.3 通用问答 / 深度研究 / 生成 PPT·Excel·Word

- **能力**：Tabbit 新标签页的三档输入模式（问答/任务/深度研究）与文件产物生成。
- **诱因**：用户真的会问；看起来最像「AI 产品」，最易当卖点。
- **拒绝理由**：
  1. 这是模型与算力的比赛，不是浏览器工程的比赛，我方优势为 0；对手是 Atlas / Comet / ChatGPT。
  2. 会把资源从「Flash 能不能挂」转移到「回答得像不像样」，后者永远追不平。
  3. 产品叙事会散：我们卖「唯一能跑 Flash 的可审计浏览器」，不是「又一个会聊天的浏览器」。
- **不做的代价**：用户想聊天会去别处。写进对外文案（明确不做通用助手）。
- **解冻条件**：M4 之后，且只做与挂机/工作流相关的一小块（例如把录制操作解释成人话），不做通用聊天。

### 2.4 85 条电商社交网页配方（对照组：游戏配方要做）

- **能力**：`WEBMCP-MAPPING.json`，14 个站点包 / 85 条能力（bilibili、x、youtube、weibo、taobao、jd、goofish、feishu-base、amazon、xiaohongshu、xiaoyuzhou、google、github、bytedance-resume）。
- **诱因**：数量即能力感。
- **拒绝理由**：
  1. 每条配方是长期维护债：站点改版即失效，14 站每周都在变，不是一次性开发成本。
  2. 只在「开放式任务」有价值，不是主场景。
  3. 无兜底：Tabbit 配方只有 DOM 一条路，DOM 变即整条作废。
- **对照结论**：**做少而稳的游戏配方（3–10 条），不做多而脆的网页配方**。技术依据：我方配方可声明「DOM 定位失败 → `findTemplate` 视觉定位 → 插件内输入」，同一条配方在 Flash 画布上也能跑。
- **规模化条件**：配方能由录制自动生成 + 失效能自动检测（断言 + 视觉兜底）；否则只做头部 10 条游戏站。

### 2.5 `chrome.*` 数据面（历史 / 书签 / 阅读列表 / 置顶站点）

- **能力**：Tabbit skill 明确列出 `chrome.history / bookmarks / readingList / topSites / sessions`。
- **诱因**：接口现成，看似低垂果实。
- **拒绝理由**：
  1. 对「挂机监督者」零用处。
  2. 一旦有，就承担一整套义务：数据不出本机的证明、脱敏、保留期、导出与删除——D 区已认定为高成本项，为一个用不上的能力付账是负 ROI。
- **解冻条件**：若将来做「跨会话上下文」，先做只读 + 本地不传出 + 明确保留期。

## 3. 放权边界（回答「我们放权也很厉害」）

承认前提：CDP 中 `Runtime.evaluate` 等于页面内任意 JS 执行，`Network` 域可见全部流量，`Fetch` 域还能改请求与响应；再加上自动化 API，理论上能拿到页面几乎所有信息。这不是漏洞，是设计。区别在于**给了谁、走哪条路、往哪个方向流、能被谁驱动**。

### 3.1 四个维度

| 维度 | 我方现状 | Tabbit |
| --- | --- | --- |
| 能力 | 大（CDP 全域在 Host 手里） | 大（Playwright 全域） |
| 入口 | 单一入口：Host 工具面（语义工具 + schema 校验） | 两条：工具面 + Playwright 直连 |
| 方向 | 以「读进上下文」为主；外发只有一条且挂审批 | 读 + 默认可用的外发（带 cookie） |
| 可被谁驱动 | Host（自有可审计代码） | Host + 模型 + 页面内容可间接影响 |

「放得更开」若指第一行（能力）——该继续做；若指第二、四行（入口与可达性）——是性质变化。

### 3.2 语义工具 vs 原始通道（设计支点）

CDP 是实现手段，不是暴露面。F0′ 四层工具面 v1 清单：

```
DOM 层      observe / extract / click / fill / navigate
视觉层      findTemplate / findColors / ocrLocate / ocrRead / capture / surfaceDetect
GM 等价层   setValue / getValue / xmlHttpRequest[sensitive] / notification / clipboard
自动化层    locate 四型 / action 原语 / workflowStep / workflowRun
```

- 清单中**没有** `runtime.evaluate`，没有「给我一段 JS 我执行」，没有 CDP 命令透传。
- Hub 现用域为 DOM / Runtime / Input / Accessibility（观察与输入）；`Network`、`Fetch` 域不在工具面，也没有透传通道。
- 模型看到的是十余个语义动作，不是两百个协议域。这是「能力大但不危险」的直接原因。

### 3.3 三条腿

| 腿 | 我方 | 说明 |
| --- | --- | --- |
| 私人数据可达 | 有 | observe/extract 可读到登录信息、订单、邮箱 |
| 不可信内容 | 必然有 | 页面本身 |
| **外发通道** | **只有一条，挂 sensitive 审批** | `GM_xmlhttpRequest` 等价面；无人值守时等于关闭 |

准确表述：不是「砍掉外发」，而是**把外发做成需要人点头的动作**。与 Tabbit 的「默认可用、带 cookie、无审批」是同一类能力的两种策略，差别在人的位置。

### 3.4 诚实边界：第二条出境腿

观察内容进入模型上下文，本身即数据出境。这条无法消除，只能压低。两者风险量级与防护手段不同：

| | 送进模型上下文 | 送进攻击者服务器 |
| --- | --- | --- |
| 谁看到 | 一个受合同约束的供应商 | 任何人 |
| 能否事后约束 | 企业协议、审计日志、可切本地模型 | 不能 |
| 防护手段 | 最小读取、裁剪、预算、本地模型选项 | **只能靠「能力不存在」** |
| 现有措施 | 精简 DOM 树、截图裁剪、`maxResultBytes`、截图不进上下文只给路径 | 外发工具挂 sensitive |

推论：正因为读能力已经放得开，更要**在「送出去」这一步守死**。

### 3.5 0→1 与 1→2

- 「多给一个读工具」：1→2，量的扩张，边际风险小，**做**。
- 「从无外发到有外发」：0→1，性质跃变，**不做**。
- 「从有审批的外发到无审批的外发」：人→无人，同样是 0→1，**不做**。

三种「放得更开」的含义与裁决：

| 含义 | 裁决 | 理由 |
| --- | --- | --- |
| A. 给 agent 更多工具（能力扩张） | ✅ 持续做 | 每加一个工具过一遍「哪些参数可被页面间接操纵」（F3 S4 第②条），sensitive 强制审批；风险可分级 |
| B. 给外部调用者直通 CDP（旁路执法层） | ❌ 不做 | Host 会变成可选组件，预算/审批/代际/回放全部旁路；Tabbit 即此形态，它的「强」与「薄」是同一件事 |
| C. 降低审批/预算阈值（真放权） | 🟡 按实测调 | S3 原则为「保险丝不是配额」，阈值本就该调；但「sensitive 降 read」不是调阈值，是拆闸 |

## 4. 可复用筛子

```
1. 是否新增「外发通道」或「私人数据可达」？        → 是：A 类红线，停
2. 是否引入不可测试的外部状态（别人的 UI/版本）？  → 是：不做
3. 是否只对「开放式任务」有用、对确定性主场景无用？→ 是：往后放
4. 是否把我们推向通用助手正面竞争？                → 是：不做
```

口诀：**凡是让「注入一次就能偷走东西」或「别人一升级我们就崩」的能力，一概不进主包。**

## 5. 真实风险清单（不装完美）

1. **Host 本身持有大权**：其 bug 等于绕过所有闸。单点风险，靠代码评审 + F3 S5 三条探针 + 单一入口控制。
2. **`Runtime.evaluate` 在页面内是任意执行**：Ruffle 注入、GM 等价面都会用到。工具面不暴露 eval，但实现层存在，属需持续审查面（尤其「注入脚本进主世界」一类）。
3. **截图会带上全屏内容**：故 F2′ 定「裁剪是视图层」，截图不进模型上下文、只给路径。
4. **模型上下文即出境**：靠精简观察、预算与本地模型选项压低，不靠表述。
