## 0. 一句话主张

> 能用指向解决的，就不需要语言；能用结构化时间解决的，就不需要视觉推理；只有需要理解和讨论的问题，才进入传统对话。
> ——【用户】

本文的立论（【AI 补】）：**指代不是一种输入方式，是一种可共享的地址。**

人指一次，产生一个地址；AI 标一次，产生同一个地址；两个地址可比对、可交换、可持久化。
语言之所以低效，不是因为它慢，而是因为它在「人 → 模型 → 选择器」这条路上每转译一次就掉一层信息。

---

## 1. 表达阶梯：四层，不许上跳

【用户】给出的顺序，本文形式化为成本递增的四层：

| 层 | 手段 | 携带的信息 | 成本 | 可用前提 |
| --- | --- | --- | --- | --- |
| 指向 | 点击、选中、框选、拖标签进来 | 目标身份 + 作用域 + 当下页面状态 + 排他性 | 最低 | 目标当下可见 |
| 结构化 | DOM/AX、表单、表格、轨迹、时间序列 | 关系、批量、顺序 | 低 | 页面有结构 |
| 视觉 | 截图、模板匹配、OCR、坐标 | 像素级外观 | 中 | 无结构（Flash / Canvas / 图片） |
| 语言 | 自然语言对话 | 意图、歧义、判断 | 最高 | 前三层都不成立 |

判据：**任何一层能解决的问题，不许上跳。** 尤其最后一条——语言只用于「需要理解和讨论」，不用于定位。

反例（也是当前所有参考产品的主路径）：给一个聊天框，让人用语言描述「左边那个蓝色的按钮」，
模型再猜、再用视觉兜底。这是把最贵的一层放在最前面，代价由用户承担。

## 2. 为什么指代强于十轮对话

【用户】一次指认携带的信息量，比人和 AI 交流十轮还强。逐项拆开：

| 维度 | 一次指认给出的 | 十轮对话才逼近的 |
| --- | --- | --- |
| 目标身份 | 精确到节点 / 区域 | 「大概是那个…不是这个…」 |
| 作用域 | 隐含（这个元素 / 这个 iframe / 这个 surface） | 每轮都要重新澄清 |
| 当前状态 | 点击瞬间的页面事实 | 描述永远是过去时 |
| 排他性 | 「就是这个」，无歧义 | 概率收敛 |
| 坐标与代际 | 天然携带 | 描述不出来 |

【用户】外部 agent 用 Playwright 交互，对人来说是个极不方便的调试过程：人只能尽量描述，
自己拆元素树一层层拨开；外部 agent 慢慢剥，不如人的一次指认。

【AI 补】把它写成转译次数：

```text
外部 agent  人 → 语言 → 模型 → 选择器 → DOM       四次转译，每步掉信息
内部 agent  人 → 同一个 TargetRef → 执行          零转译
```

这不是能力差异，是**进程边界**差异：外部 agent 拿不到你 UI 产生的地址，它只能靠人打字复原。

**由此得到本文最重要的一条合同改动**（【缺口】）：

> `TargetRef` 的产出者不止 Agent，还包括人的指代 UI。同一个类型、两个产出者、可互相传递。

这是「指代一次胜过十轮对话」唯一的工程实现方式，也是外部 agent 结构上无法复制的部分。
现有 SSOT §6.4 只写了 Agent 消费短引用，没写 human-ui 也能产出。

## 3. 共享工具：一件仪器，两个人用

【用户】最重要的一套东西，是人和 AI 能一起使用的工具：比如 DOM 元素选择，人能使用，AI 也能使用；
AI 可以标出它指向的元素，人也可以标出人指向的元素。

【AI 补】关键不是「给 AI 做一个工具，再给人做一个工具」，是**同一件仪器、两个操作者、一个共享状态**。
三条实现约束：

1. **地址唯一**：人标的与 AI 标的必须落在同一个 ID 空间里，可比对。否则「AI 标错了」这句话无法表达。
2. **来源可辨**：每个标记能回答「谁标的」（human-ui / agent / workflow），否则协作历史无法回放。
3. **可移交**：人的框能被 agent 接管继续用；agent 的框能被人修正后交回。移交点必须是可撤销检查点。

## 4. 锁定框协议：提议 → 修正 → 二次确认

【用户】老项目用相框助手做模板匹配 / OCR 时，页面上有锁定框且携带坐标系；新项目里这个锁定框
可以成为典范——AI 指出框，人拖拽拉伸修正，AI 重新识别并二次确认。

【AI 补】把它写成三态协议，而不是一个 UI 控件：

```text
propose (AI)   框 + 置信度 + 依据（模板命中 / 颜色簇 / OCR 行）
   ↓
correct (人)   拖拽 / 拉伸 / 删除 / 新增；每次改动记 delta
   ↓
confirm (AI)   用新框重新识别，回报「我在框里看到了什么」
   ↓
commit         框 + 修正历史 → Surface Recipe / 页面规则 / 锚点
```

四条要点：

- **置信度必须外化**：AI 的不确定不是一句「我猜是这里」，而是框的大小、线型、候选框数量。
- **修正成本必须低于描述成本**：拖一下 vs 打一段话。这是整个协议成立的前提，不成立就退回 §1 的语言层。
- **二次确认不可省**：不做的话，人的修正只是一次性补丁，agent 下次照错。
- **每次修改都是一条轨迹**：谁、从哪到哪、何时，可直接进审计流。

### 4.1 冻结帧指代（老项目实证，必须保留）

【AI 补】老项目 `automation-frame-assistant.user.js` 的框选不是直接在活页面上拖，而是：

```text
captureFrame(region, 'surface' | 'viewport')  →  静态帧 + previewWidth / previewHeight
在全屏遮罩层里对这张帧拖框（#bao-automation-capture-layer，box-shadow: 0 0 0 9999px 做遮罩）
pointerup 时把屏幕坐标映射回帧坐标（× previewWidth / imageRect.width）
```

理由：**指代是对某一帧的断言，不是目标的永久属性。** Flash / Canvas 一直在重绘，在活页面上拖框
等于对移动目标射击；帧一冻，人可以慢慢框，框选结果还能和对齐的帧一起存成证据。

代价：帧会过期。所以框必须带 `captureId` + `transformVersion`，映射回活页面时校验——
这正是 SSOT §6.4 `kind: 'visual'` 已有的字段，只是没被当成「人机共用的交互」来用。

## 5. 「训练」：三种含义，只有一种能交付

【用户】在浏览器里强调协作，甚至可以说是一种训练。

【AI 补】「训练」至少三种含义，混在一起会把产品做错：

| 含义 | 做不做 | 载体 |
| --- | --- | --- |
| 参数训练（微调模型） | 不做 | — |
| 上下文内适应（一次会话里越用越准） | 顺带得到 | Prompt + Page Map 历史 |
| **资产化适应（修正沉淀为可复用规则）** | **必须做，这就是产品** | Surface Recipe / 锚点 / 站点规则 |

只有第三种是可交付、可验证、可跨会话的，而且只有浏览器内部能做——它有站点身份、有持久化、有代际。
「协作即训练」要变成卖点，只能走这条路。

---

## 6. 指代回执：同构回指

【AI 补】指代会指错，人也会指错。所以 agent 必须回执，但**回执不能是文字**——
「我理解你指的是登录按钮」这句话，人要读、要判断、还可能误判。

正确形式是**同构回指**：用同一个工具、同一套视觉语言，把目标重新标一遍。
人一眼就知道对不对，判断成本接近 0。

> 规则：Agent 收到任何指代后，第一次动作前必须回指一次；回指与人的标记必须在同一坐标系、
> 同一视觉语言下可直接比对。

## 8. 技术形态：把「看见」和「摸着」分开

【AI 补，含【待实测】】锁定框有两件事，必须拆开设计：

- **看见**（渲染）：框画在哪一层。
- **摸着**（输入）：拖拽事件被谁接。

渲染层两个选项：

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| 页面内注入（老项目相框助手走的路） | 天然跟随滚动/缩放；输入穿透用 `pointer-events` 控制 | 只在网页有效；PPAPI/Canvas 里注不进去；多一个注入风险面 |
| 外壳浮层（`WebContentsView` 挂到 `window.contentView`） | 跨引擎统一（Flash 也有框）；不受页面 CSS/z-index 影响；复用现有浮层与预热 | 要自己做 Coordinate Plane；全页透明层会吞掉页面输入 |

代码事实：现有浮层就是 `window.contentView.addChildView()` 的 `WebContentsView`，靠 `setBounds` 定位
（`app/src/main/shell-overlays.ts:176`、`:190`、`:266`、`:326`），所以「框画在页面之上」这条路径本身是通的。

**老项目用血换来的教训：交互元素会污染识别输入。**

`renderPageCross()` 把命中框画在页面 DOM 上，注释明写「红框画在页面 DOM 上会被 capturePage 截进识别帧，
故每次识别发起前必须清掉」（`automation-frame-assistant.user.js:495-497`）；面板遮挡也要先折叠再识别
（`withRecognitionPanelCollapsed`，`:291`）。这不是 bug，是层次错位的必然结果——UI 和内容同住一棵渲染树。

【AI 补】这给「渲染层选外壳浮层」提供了一个比「复用」更硬的论据：`webContents.capturePage()` 只截该
WebContents 的渲染输出，不含兄弟视图。框画在外壳层，**结构上不可能进入识别帧**，不需要任何「记得清」的纪律。

**双空间已经在老项目里被点名。** `ocrRegion()` 的注释写着
`the two spaces are intentionally not assumed equal`——页面当前 CSS viewport 与固定逻辑画布并不相等，
区域必须显式携带 `viewportWidth / viewportHeight` 交给 Core 换算（`automation-frame-assistant.user.js:546-553`）。
这句话应原样进 A3 的 Coordinate Plane 合同。

输入层的建议（【AI 补】）：

- **网页标签**：全页透明指代层 + 默认 `pointer-events: none`，只在「框」的矩形内接收事件，
  框外放行 → 人机可长时间共存。
- **Flash / Canvas 标签**：进入**显式指代模式**（模态），因为游戏独占输入通道，本来就不能共存；
  退出即恢复。这与「Flash 只能接管、不能协作」的结论一致。
- 【待实测】`WebContentsView` 级别能否做到「框内接管、框外放行」的命中测试，
  还是必须靠页面侧注入层做事件分流。

## 9. 反模式

- 侧边栏聊天框作为主入口：把指代扔掉，把注意力抢走。
- 把共享工具做成 low-code 编排器：工具是给**指代**用的，不是给**编排**用的；编排归 workflow。

- 用语言描述定位（「第三个卡片右边那个按钮」）。
- 有结构却先上视觉：截图/OCR 当默认路径。

### 三条「搬家」原则（不是重写）

1. **形状保留，层次上提**。surface / region / point 三种指代 + 一个回执，这套形状是对的，
   缺的是把它们从「某个脚本的私有用具」变成 Perception / Capability 层的**共享仪器**。
2. **框要变成可序列化的断言**。老项目的框是「纯视觉 + 一个分数」，语义全靠人脑补——
   人知道自己在框什么，agent 不知道。搬到新架构必须补：坐标系、代际、置信度、依据（evidence）、
   产出者（human-ui / agent）。否则 agent 拿到框也不知道能不能信。
3. **失效要显式**。老项目靠 viewport 快照比对（`surfaceViewportChanged`，`:651`）+ resize 后重检测，
   失败即要求重选。这是代际的手工版，方向对，但判定条件太窄——它只认窗口尺寸变化，
   不认导航、不认引擎切换、不认绑定重建。

### 一条反向提醒

老项目这套交互的隐含前提是**人在场**：框选、点击候选、拖动修正，全都要求人看着屏幕。
搬到「人机协作」里不能照抄——agent 没有眼睛在场，它只有 capability 返回值。所以同一件仪器必须
同时支持「人看得见」和「机器读得出」两种消费方式，这也是本文 §3「同一件仪器、两个操作者」的由来。
